# What every set copies from this repository

`simai/ui-view` is the first reference component set built to standard
`simai.component-set` 1.0.0 with its documentation site in the same
repository. This file sorts what is here into the part every set (admin,
chat, mail, editor, chart, effects) copies unchanged, the part it fills in
for itself, and the part that is `view`'s own, so the shared Docara set
template and the shared set scripts can be extracted next.

Legend: **generic** — copy unchanged; **fill** — same file, set-specific
values; **own** — `view` only.

## Repository layout

```text
LICENSE.md, AUTHORS, CITATION.cff     fill   product name; Pro or Apache-2.0 text
README.md, CLAUDE.md, CHANGELOG.md    fill   set name, elements, rules for agents
package/                              the set (standard simai.component-set)
  set.json                            fill   the passport: id, title, licence, families, components
  framework.lock.json                 fill   the pinned ui-source revision (same as set.json)
  package.json                        fill   @simai-studio/<id>, licence, simai.set
  README.md                           fill
  src/smart/<folder>/                 own    the components
  tests/*.test.mjs                    own    the components' tests
  tests/set-passport.contract.test.mjs generic passport against schema, folders, rules, registry; a relation may name a rule of a required set
  tests/set-registry.mjs              generic the registry check shared with the script
  tests/browser/*.browser.mjs         own    the components' browser probes
  tests/fixtures/                     own
  scripts/overlay.mjs                 generic* PACKAGE_NAME is the only literal (could read set.json id)
  scripts/test.mjs                    generic the CROSS_CUTTING list is the Framework's, not the set's
  scripts/run-manifest-probes.mjs     generic --set <id>=<output> per required set
  scripts/run-browser-probes.mjs      generic* the needsLab list names this set's lab probes; --set <id>=<output>
  scripts/run-first-paint.mjs         generic
  scripts/check-registry.mjs          generic
  scripts/gates.sh                    generic* the package id `view` in three lines; --set <id>=<dir>
  scripts/stage-npm.mjs               generic (effects adds its catalogue)
site/                                 the Docara site
  composer.json                       fill   pins simai/docara exactly
  docara.json, docara.authoring.json  fill   title, branding
  simai-framework.lock.json           generated by the materializer; committed
  contracts/generated/*               generated by the materializer; committed
  scripts/materialize-framework-runtime.php generic* constants: the pair (5 revisions) and PACKAGES
  scripts/build.sh                    generic* the build output path names the set id
  scripts/serve.mjs                   generic
  scripts/evidence.mjs                generic* the pages and the demo click are view's
  content/ru/                         see «Site skeleton»
  examples/                           own
docs/SET-TEMPLATE.md                  this file
docs/DOCARA-REQUESTS.md               what Docara should take over
docs/evidence/                        screenshots and gate results of a run
```

`generic*` marks a file with a set literal that the extraction should turn
into a value read from `package/set.json` (`id`, `components[].folder`) or
from the site's lock.

## Site skeleton (decision 2026-11-03, point 9)

The five sections the standard requires, in this order, as files:

| Section | File | Generic part | Set part |
|:---|:---|:---|:---|
| Обзор | `content/ru/index.md` | the headings «Что входит в набор», «Лицензия», «Совместимость с SIMAI Framework», «С чего начать»; the licence text of the class; the compatibility table | the component table, the planned views |
| Подключение | `content/ru/connection.md` | the whole page with the set id substituted: the `data-sf-sets` line, the `SF_BOOT_CONFIG.packages.<id>` form, the former-tags note | the example element |
| Компоненты | `content/ru/components/<folder>.md` | the page order: what it is, live examples, parameters, intents, «См. также» | the text and examples |
| Демо | `content/ru/demos/<name>.md` | the page order: what the screen is, the screen as one fullscreen example, «Из чего собран» | the screens |
| Изменения | `content/ru/changes.md` | one `##` per set version, newest first | the entries |

The compatibility table and the connection line hold values the set already
has (`set.json` `framework`, the receipt's `framework.release`, the npm
version of the pair): the template should generate them between
`<!-- docara:generated -->` markers instead of having them typed.

Navigation order is set by `*.page.json` and `section.json`
(`navigation.order`: 10 Обзор, 20 Подключение, 30 Компоненты, 40 Демо, 50
Изменения). `docara.authoring.json` maps `components/**` to the reference
profile and `demos/**` to article.

Live examples are Docara project examples, `examples/<id>/index.html` and
`index.js` (and `index.css`), referenced with
`:::example {id="<id>" label="…"}`; demos add `fullscreen=true`. Each example
feeds its component either directly (`setColumns`/`setRows`) or through a
host object on the page (`setHostPort`) that answers the component's intents
the way a server would; the data is realistic and Russian.

## The gates (same for every set)

`package/scripts/gates.sh <workspace>` runs, over the commit at HEAD:

1. two byte-identical builds (ui-builder `verify-package-reproducibility.cjs`);
2. the receipt (`write-package-receipt.py --ui --registry`), which also checks
   the passport against the name registry at ui-source main;
3. the unit suite in the overlay of the pinned ui-source (`--committed`);
4. the passport against the registry at main (`check-registry.mjs`);
5. the manifest probes of every `probe.json`;
6. the browser probes;
7. the first paint, `check` (committed snapshots current) and `gate`
   (1280 and 390 px, CLS).

A set that requires another (`requires_sets` in `set.json`) is probed with
that set beside it, as a page declares both (`data-sf-sets="chat view"`):
`gates.sh` reads `requires_sets` and passes `--set <id>=<dir>` to the manifest
and browser probes, `<dir>` being the required set's released output (the
folder holding `smart/rule.js`), `../ui-<id>/package/dist` by default or
`--set <id>=<dir>` on the command line. The probes lay it under
`smart/smart/set-<id>/` and declare it with its own base. A relation to a rule
of a required set (`cl-chat-message` to `cl-view-properties`) is met by the
names the registry gives that set's owner: in `set-passport.contract.test.mjs`
here, in ui-source `tests/loader-relations.contract.test.mjs` from ui-source
2874cb5d on (with `SET_ROOT`), and in ui-builder `write-package-receipt.py`
from eb0a3c9 on (with `--registry`). A set pinned to a pair older than that
ui-source keeps `loader-relations` out of `CROSS_CUTTING` and carries the set
half, as ui-chat `package/tests/loader-relations-set.contract.test.mjs` does.

When the free side is a ui `distr`, the browser probes lay it out with
symbolic links and copy the free `smart/smart` with `dereference: true`, so
the set's folders land in the probe output, never inside the free `distr`.

Then `site/scripts/build.sh <workspace>` builds the site over that same
build, `site/scripts/serve.mjs` serves it on 127.0.0.1 with CORS (the
examples run in sandboxed frames), and `site/scripts/evidence.mjs` takes
the review screenshots and fails if a set element on a page never upgrades.

Not here yet, as in the standard's rollout: linkage (unit passports and the
release inventory), the release route (`publish-package-release.sh`, tag
`<set>-<12>`, `package/dist/`), the compatibility index row, and CI.

## What is `view`'s own

- The three components and their 60 browser probes and ~55 unit tests,
  copied from ui-pro with the package-wide tests narrowed to the set's
  folders.
- The probe exceptions: four lab-driven probes skipped
  (`composition-routing`, `loader-hidden-tab`, `table-intents`,
  `table-search-caret`) and one `.cli.js`, as in ui-pro.
- The examples and the two demos (orders, staff).
- `requires_sets` is empty; `admin` will require `view`.
